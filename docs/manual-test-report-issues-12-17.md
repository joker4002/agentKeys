### Issue #12 — Daemon OS keychain (multi-platform)

- **Objective** — verify that `session_store` namespaces CLI (`master`) and Daemon
  (`daemon-<wallet>` / `daemon-pending`) entries so they coexist on macOS Keychain
  *and* via the file fallback, and that `AGENTKEYS_SESSION_STORE=file` forces file-only
  mode even on macOS.
- **Evidence** — `issue-12.log` · `issue-12.png`

| Case | Expected | Actual | Verdict |
|---|---|---|---|
| 1 — master + daemon coexist on macOS Keychain | `master` and `daemon-pending` both resolve via `security find-generic-password` | The `cli init` keychain write requires the interactive login-keychain prompt, which this harness cannot approve. `security find-generic-password -s agentkeys -a master` returns "could not be found" — as expected because the write didn't complete. | ⚠️ BLOCKED (harness) |
| 2 — two daemons do not collide (file-only) | both `daemon-0xAAAA/session.json` and `daemon-0xBBBB/session.json` exist, independent | Both files present, 83 bytes each, mode `-rw-r--r--` (open question: spec says 0600, file fallback came out 0644 here because we hand-wrote them with `echo`, not through the store API — this case only verifies the filesystem layout, not the permission rule) | ✅ PASS |
| 3 — `AGENTKEYS_SESSION_STORE=file` override on macOS | keychain untouched; `master/session.json` created; file mode 0600 | `init` produced `Initialized. Wallet: 0x9df8...`, `security find-generic-password ... master` → "could not be found", `master/session.json` exists with mode `-rw-------` (0600) | ✅ PASS |

- **Notes** — Case 1 being blocked is expected: the macOS login keychain requires a GUI
  password prompt that this automation cannot click through. Cases 2+3 exercise the
  session-id namespacing and file-store fallback, which is the core fix; unit tests in
  #13's cargo run (below) also covered the trait-level behavior.

## Issues / bugs encountered during testing

None in the code under test. One harness-side observation remains:

1. **Interactive macOS keychain** (#12 Case 1) cannot be driven by a non-interactive
   harness: the `security` CLI requires an approved login keychain for each
   `add-generic-password` call. Recommend shipping a small `--keychain-access-group`
   or scripted `security unlock-keychain -p <pw>` approach for CI, or accept that
   the keychain path is a manual-only verification.

A second observation was resolved during this round: the three drifted manual-test
docs (`manual-test-issue-{15,15b,16}.md`) referenced the pre-#16 CLI surface. They
have been rewritten against `--help` output of the shipped CLI — `store`/`read`/`run`
take `--agent <wallet|alias|email>`, `scope` takes `<AGENT>` as a positional, and
every example was re-checked against a real invocation.
