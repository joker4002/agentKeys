AgentKeys 是什么？

你可以把它理解成一个专门给 AI agent 管 API key 的“钥匙管理员”。 人先把 key 存进去，agent 需要时再按权限去取，不用再把一堆 key 塞进 .env，出了问题也能随时收回。

人负责授权 Agent 按需取用 支持撤销和恢复
当前仓库快照

这个页面描述的是当前项目形态，不把未来规划说成已经做完的能力。

管理端

当前是 CLI，长期更合理的形态应该是 GUI。

Daemon

Agent 侧 sidecar，负责配对、恢复、MCP 接口。

Backend

v0 是 mock server，未来目标是 Heima TEE 后端。

MCP

MCP 是 agent 的访问接口，不是整个产品本体。

一句话说清楚

如果你有技术背景，可以先把它想成： GUI 管理端 + Agent Sidecar + 后端凭证服务。 Agent 通过 MCP 按需取钥匙，但 MCP 只是访问接口，不是整个产品本体。

它是什么

给 AI Agent 发钥匙的中间层

重点不是“把密码存起来”，而是让 agent 在需要的时候拿到 API key，而且只能拿到它该拿的那一把。

给谁用

给跑 Agent 的开发者和基础设施团队

典型用户包括 Claude Code、OpenClaw、Codex 风格环境的使用者，以及自建 agent sandbox / MCP 工具链的工程团队。

解决什么

怎么发 key，怎么限权，怎么收回

它把三件麻烦事标准化：给 agent 发 key、把不同 agent 的权限拆开、在 sandbox 重建或 agent 出问题时快速撤销和恢复。

从软件形态上看，它到底是什么？

它不是单纯的 “MCP server + client”。更准确地说，它是一套分布式凭证系统，MCP 只是 agent 访问这套系统的一层协议接口。

产品形态

三层结构

  • 人类管理端：当前是 CLI，最终更应该演进成 GUI。
  • Agent Sidecar：`agentkeys-daemon` 跑在 sandbox 里，贴着 agent。
  • 后端凭证服务：负责 session、scope、audit、pair / recover、credential storage。
不是它的地方

MCP 不是产品本体

  • MCP 只是给 agent 暴露 `get_credential` 这类能力的入口。
  • 人类端不应该长期停留在 CLI，而应该走向 GUI 审批、审计、权限查看。
  • 所以最准确的表述是：AgentKeys 包含 MCP，但不等于 MCP。

流程图版理解

人类这边做什么

初始化身份、存储已有 key、批准配对、撤销访问、查看审计。当前这些动作通过 CLI 完成，但长期更适合 GUI。

Agent 这边做什么

不直接碰 `.env`，而是经由 daemon 的 MCP 工具获取受 scope 限制的 credential。

后端这边做什么

负责 session、child session、credential storage、audit、rendezvous、auth request。

主流程 A

Store → Use → Revoke

  • 当前是用 CLI 把 `my-agent + service` 对应的凭证写入后端。
  • Agent 经由 daemon 发 MCP 请求，只能读到属于当前 scope 的 credential。
  • 一旦 agent 风险升高，主控端可以 revoke，之后读取就会被拒绝。
agentkeys store my-agent openrouter sk-...
Agent --MCP--> agentkeys.get_credential("openrouter")
agentkeys revoke my-agent
主流程 B

Pair / Recover

  • daemon 启动时向后端创建 pair 或 recover 请求，拿到 pair code。
  • 主控端当前通过 CLI 确认配对码并批准请求；产品体验上后面更适合迁移到 GUI 审批流。
  • 这样即使云端 sandbox 是一次性的，agent 也不需要每次重配外部服务凭证。
agentkeys-daemon --recover my-agent
...显示 Pair Code...
agentkeys approve ABCD-EFGH

当前项目做到哪一步

这里区分“已经在代码里存在的能力”和“目前还停留在设计文档里的能力”，避免把愿景误读成现状。

已经存在

当前仓库里已经有的东西

  • Rust monorepo 与共享类型、`CredentialBackend` 契约。
  • Mock backend：session、credential、audit、rendezvous、auth request。
  • 当前的人类管理端是 CLI，支持 `init`、`store`、`read`、`run`、`revoke`、`usage`、`approve` 等命令。
  • `agentkeys-daemon` 已支持启动、配对、恢复和 MCP stdio 服务。
  • MCP 侧已提供 `agentkeys.get_credential` 与 `agentkeys.list_credentials`。
尚未完整落地

接下来更像产品化方向的东西

  • 人类管理端从 CLI 升级成 GUI，尤其是审批、审计、agent 列表和权限查看。
  • `agentkeys.provision` 的完整自动开户 / 自动取 key 流程。
  • 面向云 LLM 环境的 npm daemon 分发方案。
  • Heima TEE 作为正式后端替换当前 mock server。
对有技术背景的人来说，最好的理解方式是： AgentKeys 正在把 “AI agent 用凭证” 这件事，做成一个独立系统层。 现在已经有核心骨架；未来要补的是 GUI 管理端、自动 provision 和更强的可信后端。
